# ClinicOps – Phase 2 Documentation
## Identity Management, Access Control, and Security Auditing

### 1. Project Overview

Phase 2 expanded the ClinicOps healthcare IT lab by focusing on identity administration, role-based access control, file sharing, and Windows security auditing.

The objective was to create and manage fictional healthcare user accounts, configure access permissions based on job responsibilities, test permitted and restricted file operations, and investigate the security events generated by those activities.

Phase 1 used a separate `clinicops.test` domain on a Windows Server 2025 virtual machine. For Phase 2, I used the existing MSSA training environment and created a dedicated ClinicOps organizational unit within the preexisting `adatum.com` domain.

All accounts and activities in this project are fictional. No real patient information or protected health information (PHI) was used.

### 2. Lab Environment

Phase 2 was completed using the existing MSSA Windows Server environment.

**Environment configuration**

- Domain: `adatum.com`
- Domain controller: `LON-DC1`
- Member server: `LON-SVR1`
- Client computer: `LON-CL1`
- Domain NetBIOS name: `ADATUM`
- Operating system: Windows Server 2019
- File share: `\\LON-DC1\ClinicOps`
- Local folder: `C:\ClinicOps`

I initially investigated creating another Hyper-V virtual machine for Phase 2. However, nested virtualization was unavailable in the provided environment. Instead of modifying the existing domain configuration or making domain-wide changes, I created a dedicated `ClinicOps` OU within `adatum.com` and kept the project accounts and groups organized there.

### 3. Active Directory Organizational Unit and Security Groups

Created a dedicated `ClinicOps` organizational unit in the existing `adatum.com` domain and enabled protection against accidental deletion.

Created three Global Security groups to represent different healthcare job functions:

- `ClinicOps-Clinical-Staff`
- `ClinicOps-IT-Admins`
- `ClinicOps-Compliance`

These groups were used to organize access according to each role's responsibilities.

### 5. NTFS File System Permissions

Created the `C:\ClinicOps` folder on LON-DC1 to serve as the shared location for the simulated healthcare environment.

Configured NTFS permissions through the Windows folder security settings. The three security groups received different permissions based on their assigned responsibilities.

| Security group | NTFS permission |
|---|---|
| ClinicOps-Clinical-Staff | Modify |
| ClinicOps-IT-Admins | Full Control |
| ClinicOps-Compliance | Read & Execute |

Preserved the existing inherited system and administrator permissions while adding explicit permissions for the ClinicOps groups.

![ClinicOps NTFS permissions](06-Screenshots/Phase%202%20Screenshots/13-ClinicOps-NTFS-Permissions.png)

### 6. SMB Share Configuration

Created an SMB network share named `ClinicOps` using Server Manager and configured its share permissions separately from the NTFS permissions.

| Security group | SMB share permission |
|---|---|
| ClinicOps-Clinical-Staff | Change |
| ClinicOps-IT-Admins | Full Control |
| ClinicOps-Compliance | Read |

Verified the configured share permissions using PowerShell:

`Get-SmbShareAccess -Name "ClinicOps" | Format-Table AccountName, AccessControlType, AccessRight -AutoSize`

Network access was controlled by the combination of SMB share permissions and NTFS permissions. The more restrictive effective permission determines what a user can do through the network share.

### 8. Windows Security Audit Policy Configuration

After completing the access-control tests, I configured Windows security auditing to capture file-system and network share activity.

Initially, the relevant audit policy subcategories were set to No Auditing, and the ClinicOps folder did not have auditing entries configured.

Used the `auditpol` command to review the local audit policy and enabled both Success and Failure auditing for the following subcategories:

- File System
- File Share
- Detailed File Share

Configured these settings locally on LON-DC1 rather than changing domain-wide Group Policy settings.

### 10. Security Event Generation and Investigation

Generated file-access activity using the fictional accounts and reviewed the resulting security events through Event Viewer.

**Successful access – Event ID 4663**

Used Hermione's account to access the network share, open an existing file, create a folder and text file, write content, and delete the test items.

Windows recorded successful audited file-system access activity. Event ID 4663 provided evidence of audited access to the file-system object.

![Clinical Staff file access audit events](06-Screenshots/Phase%202%20Screenshots/25.%20Clinical%20Staff%20File%20Access%20Audit%20Events.png)

**Unsuccessful access – Event ID 5145**

Used Minerva's account to access the network share and read an existing file. Attempts to create a folder and text file were denied.

Windows recorded an unsuccessful detailed network share access check. Event ID 5145 provided evidence of the failed access attempt.

An Audit Failure event indicates that an access check was unsuccessful. It does not automatically indicate malicious activity or a security compromise.

### 12. Troubleshooting and Lessons Learned

Several issues required troubleshooting during Phase 2.

**Nested virtualization limitations**

The MSSA environment did not support the additional virtualization capabilities needed to create another Hyper-V virtual machine. I adjusted the approach by using a dedicated ClinicOps OU within the existing training domain.

**Network share access**

The share initially produced an error when accessed through File Explorer directly on LON-DC1. I verified the share configuration, SMB service, network connectivity, and access through command-line tools. The share worked successfully from LON-CL1, so I used the client computer for the role-based access tests.

**SMB share permissions**

An initial share configuration contained an unexpected Everyone Deny entry. I rebuilt the empty share using Server Manager and verified the resulting permissions through PowerShell.

**Missing audit events**

The first review did not show the expected security events because the relevant audit policy settings and folder-level auditing entries had not been configured. I enabled the required audit subcategories, added the folder auditing entries, and generated new test activity.

**PowerShell event output**

The initial security event query returned more information than was useful for reviewing the results. I refined the output to focus on event IDs, account names, timestamps, and audit results.

These issues provided practical experience troubleshooting Windows Server configuration, network shares, access permissions, and security event collection.
